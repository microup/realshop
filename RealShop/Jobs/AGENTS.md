# AGENTS.md — RealShop/Jobs/

## Что здесь

Сервисы механики задания «собрать машину с нуля» (0.3.11-dev8). Harmony-хуки живут в `Patches/JobOfferPatches.cs` (генерация, принятие, отмена), `Patches/JobPatches.cs` (слот, требования, завершение) и `Patches/CarStripPatches.cs` (зачистка остова); этот слой не ставит патчи и не трогает UI.

## Правила этого уровня

- Признак нашего задания — `Job.MissionID == BuildJobService.Magic` при `IsMission == false`: поле сериализуется игрой, поэтому маркер переживает save/load без новой схемы сохранения. Число не менять и не ставить его ванильным заданиям.
- `id` задания: `max(id)+1` по текущему списку, но не меньше `BuildJobLastIssuedId + 1`, и далее шаг вперёд по занятым id. `BuildJobLastIssuedId` сохраняется в `RealShop.cfg` (`RememberBuildJobId` → `MelonPreferences.Save()`), потому что из него и из `PaidJobs` вычисляются требования и защита от повторной выплаты: повтор id = чужие требования и невыплаченная награда.
- Harmony выполняет **postfix даже когда prefix вернул `false`** (оригинал пропущен): postfix `GameScript.EndJob` обязан проверять `ref bool __runOriginal` и выходить при `false`, иначе заблокированное завершение выплатит награду.
- **Гейт завершения не имеет права падать открыто** (0.3.11-dev20, по итогам ревью): `catch` в prefix `GameScript.EndJob` не должен заканчиваться `return true` — исключение в `Validate` (чтение `carParts`, `GetDetailsCondition`, `GetInteriorCondition` на остове, где списки пустые) открывало путь к выплате ×5 для недостроенной машины. При `BuildJobBlockEarlyFinish` исключение обязано блокировать завершение (`return false`) с Warning `EndJob gate failed`; открытое завершение остаётся только как явное поведение при `BuildJobBlockEarlyFinish = false`.
- **Префикс, пишущий `__result`, обязан возвращать `bool` и `false`** (0.3.11-dev26, CRITICAL по ревью deepseek, проверено по декомпилированному 0Harmony `HarmonyManipulator.WritePrefixes`): флаг `__runOriginal` выставляется только если среди префиксов есть возвращающий `bool` (или принимающий `ref bool __runOriginal`); `void`-префикс оригинал **не** пропускает, и оригинал перетирает записанный `ref __result`. То есть «форс геттера» на `void`-префиксе — молчащая пустышка. Образец: `BuildJobInteriorConditionGuardPatch`/`BuildJobDetailsConditionGuardPatch`.
- **Состояние Harmony (`__state`) передаётся только через `ref`-параметр, префикс возвращает `bool`/`void`** (0.3.11-dev26, live: `Prefix patch … has return type System.Single[], but only `bool` or `void` are permitted` — из-за этого **весь класс патча** не навешивается, и защита рамы молча исчезла). Локаль состояния объявляется как `ParameterType.OpenRefType()` и привязана к объявляющему типу класса-патча, поэтому `ref float[] __state` — корректная форма для ссылочного типа.
- **Машина не может быть без данных мотора**: `MainTabData.SetupData` и `EngineTabData.SetupData/SetupPowerAndTorqueData/SetupSwapOptions(CarLoader)` читают данные двигателя, и при подавленном `CreateEngine` вкладка «Информация» показывает только шильдик, а вкладка двигателя теряет «Варианты замены» (подтверждено live в dev22 и dev25). Поэтому мотор создаётся игрой, а **гасится объект** (`BuildJobStripEngineObject`, дефолт true, `CarLoader.GetEngine().SetActive(false)` в проходе зачистки): машина визуально без мотора, данные и вкладки живые, мотор приезжает с процентом зачистки (1 %), а не готовым. Откат — cfg-ключ в false, без пересборки.
- **Требование по двигателю = проверка типа, а не факта наличия** (0.3.11-dev26): `CarLoader.EngineParams.Type` (id установленного мотора, `EngineParams` — структура) сравнивается с id из `swapoptions` кузова; строка заказа показывает требуемый тип и живое состояние (`установлен` / имя установленного / `отсутствует`), `Validate` не пропускает сдачу заказа, пока тип не совпал. Проверка `HaveEngine()` для требования непригодна: объект мотора создан игрой всегда.
- **Рама живёт НЕ в `carParts`** (0.3.11-dev31, доказательство по дампу: у `CarLoader` ровно один список деталей — `carParts`/`GetCarParts()`, и в именах из live нет записи рамы/шасси). Панель берёт `MainTabData.FrameCondition` (объект `Condition` на вкладке UI), а `BuildJobServiceValidation.FrameCondition(loader)` — наша аппроксимация по `StructureCondition` деталей. Писать 1 % в раму через `carParts` невозможно; сначала читать `[BuildJob] frame owner:` (компоненты `GetRootTransform()` и фактические `Condition`/`StructureCondition` у `body` и `details`).
- **Объекты колеса — не меша колеса**: `GetWheelFL/FR/RL/RRHandle()` содержит 28 `MeshRenderer`, их отключение не скрывает шину и диск (live dev29: `wheels=28`, а колёса на скрине). Арбитр «колёс нет» — только игровые `GetMissingWheelTypes()` и `CheckCarHaveMountedWheel()`: пока `missing=None mounted=CanDrive`, игра считает колёса установленными, и никакой косметикой этого не изменить. Родной путь один — подавление `CreateWheels`/CreateWheelsIO` (ключ `BuildJobStripWheels`).
- **`SetRandomMissingSuspension(0,100,11,11)` вызывается без исключения и подвеску не снимает** (live dev29): семантика `minMissingParts`/`maxMissingParts` не доказана (тела IL2CPP — заглушки). Перед новым подходом читать diagnostic `suspension objects: transforms=N names=…` (`LogSuspensionNames`, обход `GetRootTransform()`).
- **Задание обязано иметь работу**: `jobPartsCount = 0` + пустые `task.Parts` + `CanDelete = true` — игра чистит такое задание (гипотеза самоотмены через ~8 с после взятия, live три прогона подряд). С 0.3.11-dev30 `jobPartsCount` берётся из шаблона (`TemplatePartsCount`, минимум 1), `CanDelete = false`, и оба поля печатаются в логе сборки заказа. Проверить live.
- **В `CarLoader.carParts` нет подвески и колёс** (0.3.11-dev29, live `part names:`): там только кузовные панели плюс агрегаты `body` и `details`. Снимать подвеску префиксами имён невозможно — для неё есть родной `CarLoader.SetRandomMissingSuspension(chanceToComplete, chanceToMissing, min, max)` (cfg `BuildJobStripSuspensionParts`, дефолт 11). Колёса живут в `CarWheelsData`/объектах `GetWheelFL/FR/RL/RRHandle()`, сеттера «колёс нет» нет (`GetMissingWheelTypes()` только читает, флаги `MissingWheelTypes` = None/FrontLeft/FrontRight/RearLeft/RearRight).
- **Колёса убирает игра, а не мод** (пользователь, 0.3.11-dev29): игра не даст поставить колёса на место, которое она «не видит», поэтому косметическое скрытие выключено по умолчанию (`BuildJobStripHideWheels = false` + миграция), а родной путь — подавление `CreateWheels`/`CreateWheelsIO` одним ключом `BuildJobStripWheels` (дефолт false: пара задокументирована как вешающая приезд, включается осознанно). Проверка состояния в логе зачистки: `missing=<MissingWheelTypes> mounted=<CheckCarCanDriveState>`.
- **Отключать GameObject колеса нельзя**: вместе с ним гаснут коллайдеры, и правый клик по машине перестаёт открывать радиальное меню (проверено live в dev27/28). Если скрытие всё же нужно — выключать только `MeshRenderer` (`HideRenderers`), коллайдеры остаются.
- **`pending=writes` проверяется только на первом применении** (0.3.11-dev29): повторный проход законно даёт 0 скрытых рендереров и 0 снятых деталей (уже сделано), и прежняя логика навсегда оставляла маркер несохранённым.
- **IL2CPP-стек обрывается на нативной границе** (0.3.11-dev29, live): `System.Diagnostics.StackTrace` из Harmony-постфикса даёт только `Postfix <- DMD<CancelJob> <- DMD<...>_il2cpp`. Нужен `UnityEngine.StackTraceUtility.ExtractStackTrace()` (в этой версии Unity нет `CaptureStackTrace`).
- **Никогда не звать игровые методы-писатели по подавленной категории** (0.3.11-dev28, live): `CarLoader.TweenInteriorConditionAndDust(...)` на машине, у которой салон не создавался (`CreateInterior` подавлен), бросает `NullReferenceException` внутри игрового метода — MelonLoader печатает `[ERROR] Exception in Harmony patch of method void CarLoader::TweenInteriorConditionAndDust`. Если состояние категории нужно показать «как будто её нет», форси **геттер** и компенсируй `Validate`/`IsRequirementMet`/строку заказа, иначе заказ станет невыполнимым. Образец: `InteriorAbsent` (окно guard ИЛИ сохранённый `BuildJobConditionJobId`) + `InteriorNotDelivered()` в валидации + строка «ИНТЕРЬЕР: не приезжает».
- **Словарь имён деталей нельзя угадывать** (0.3.11-dev28): live `unmounted=0` при непустом списке префиксов означает, что имена не совпали. Средство диагностики — одна строка `[BuildJob] part names: job=… names=…` (`LogPartNames`, один раз на заказ, срез 400 символов); список живёт в cfg `BuildJobStripUnmountPrefixes` и правится без пересборки.
- **Цифры панели «СОСТОЯНИЕ» надо ПИСАТЬ в состояние игры, а не подменять геттеры** (0.3.11-dev27, live: после отмены заказа guard закрылся через 0.7 с, и панель показала игровые 58/64/58 %). Форс геттера живёт только в окне guard, а форс по сохранённому id враньём лёг бы и на `Validate` (он читает те же геттеры) → заказ стал бы невыполнимым. Поэтому зачистка пишет правду: салон в 0 через `CarLoader.TweenInteriorConditionAndDust(0f, 1f, 0f)` (когда `CreateInterior` подавлен), детали в `Unmounted = true` по префиксам имён, объекты колёс (`GetWheelFL/FR/RL/RRHandle()`) выключаются. Форс геттеров остаётся только страховкой внутри окна.
- **Миграции cfg привязаны к схеме, а не к значению по умолчанию** (0.3.11-dev27, вывод ревью): `MelonPreferences.CreateEntry` для **нового** ключа пишет в существующий cfg текущий дефолт, поэтому миграция по совпадению со старым дефолтом для нового ключа никогда не сработает, а пользовательское значение, совпадающее со старым дефолтом, откатывается каждый запуск. Образец: ключ `BuildJobConfigSchema` создаётся со значением **0**, `RepairBuildJobConfig` выполняет миграции только при `Value < ValueBuildJobConfigSchema` и после них ставит схему; починка текстовых ключов (`RepairTextEntry`) продолжает работать каждый запуск, она лечит порчу ASCII, а не миграцию.
- **Зачистка не считается применённой, если писать было не во что** (0.3.11-dev27): `TryApply` ставит `_appliedJobId` и сохраняет маркер только когда `unmounted > 0` или `wheels > 0` (или cfg ничего и не просит — `StripWritesRequested`); иначе в логе `pending=writes` и watchdog повторяет в пределах `BuildJobConditionReapplyMax`. Иначе один неудачный проход навсегда помечает зачистку выполненной, а колёса и подвеска остаются на машине до конца заказа.
- **Рама теперь тоже 1 %** (пользователь изменил требование: «рама 1 % процент а пишет 58»): дефолт `BuildJobStripKeepFrame = false`, миграция `MigrateKeepFrame` меняет прежнее значение `true` только по точному совпадению. Снимок/восстановление `StructureCondition` вокруг `SetConditionAll` остаются в коде и пропускаются, когда раму не сохраняют; ключ обратно в true — штатный способ вернуть защиту рамы.
- **Колёса и подвеска снимаются, а не подавляются** (0.3.11-dev27): `CreateWheels`/`CreateWheelsIO` в список подавления вносить нельзя (вешают приезд). Игрового сеттера «колёса отсутствуют» нет (`GetMissingWheelTypes()` только читает, `CarWheelsData`/`Wheel` = Tire/Rim/Width/Size/Profile/ET), поэтому выключаются объекты колёс; подвеска снимается через `CarPart.Unmounted = true` по префиксам имён (`BuildJobStripUnmountPrefixes`) — тот же механизм, что и для кузовных панелей. `SetRandomMissingSuspension(...)`/`SetAllPartsMissing()` не используются: тела IL2CPP — заглушки, семантика аргументов не доказана. Оба действия только внутри guard-окна, в каждом успешном проходе; аварийные выключатели — cfg-ключи `BuildJobStripHideWheels` и пустое значение `BuildJobStripUnmountPrefixes`.
- **Несозданная категория состояния показывает 0 %, а не 1 %** (0.3.11-dev25, требование пользователя «если интерьера и запчастей нет то там не может быть 1 %»): `CarLoader.GetInteriorCondition`/`GetDetailsCondition` на пустом наборе детали возвращают не 0, а игровую константу (live: ИНТЕРЬЕР 66–67 % при снятом салоне), поэтому состояние форсится в префиксах геттеров (`BuildJobInteriorConditionGuardPatch`/`BuildJobDetailsConditionGuardPatch` в `Patches/JobConditionPatches.cs`): 0, если `BuildJobStripMethods` подавляет соответствующий `Create*`, иначе процент зачистки. Форс живёт **только внутри guard-окна**: геттеры читает UI любой машины, а вечный форс по сохранённому id показывал бы 0 % после ремонта игрока и делал бы `Validate` непроходимым. Порог завершения заказа при пустом наборе обеспечивает не геттер, а `BuildJobMinMountedParts` + требование «все детали установлены».
- **Рама не участвует в зачистке** (0.3.11-dev25, «везде 1 %, только рамка»): `BuildJobStripKeepFrame` (дефолт true) пропускает `CarPart.StructureCondition` в попартном проходе, а префикс/постфикс на `CarLoader.SetConditionAll` снимает `StructureCondition` в `float[] __state` и восстанавливает его после того, как игра отработает с 1 % — иначе рамa (среднее `StructureCondition` по установленным) уехала бы в 1 % и требование «рама >= N %» стало бы невыполнимым. Тело `SetConditionAll` — IL2CPP-заглушка, какие именно поля он пишет статически не доказать, поэтому защита двухслойная; лог `condition strip: … frame=kept|N%`.
- **Двигатель выбирается из списка кузова и НЕ устанавливается** (0.3.11-dev25): `CarData.GetEngineSwapOptions(carFile, configVersion)` читает `swapoptions=` из секции `[6_engine]` того файла конфига, который заказ реально загрузит (фолбэк `config.txt`), `TryCreateJob` берёт один вариант случайно и кладёт в cfg-пару `BuildJobEngineJobId` + `BuildJobEngineType` (одна пара на процесс — одно активное задание, `ClearActiveJob` её снимает, осиротевшая запись инертна, потому что `EngineTypeFor` сверяет id). Отображаемое имя берётся из игровой таблицы `StreamingAssets/Localizations/<Language>.txt` по ключу `!<id>=` (в кэше; язык берётся у `BuildJobText.Russian`), поэтому строка заказа совпадает с игровым списком «Варианты замены». Требование проверяет `Validate` через `CarLoader.HaveEngine()`, строка — индекс 5 в `RequirementLines`: если слотов в окне меньше шести, строка молча пропадает (число слотов печатает лог `issues: … slots=N`), требование при этом остаётся.
- **Осознанный размен dev25:** подавление `CreateEngine`/`CreateEngineAsync` возвращает известный по live-логу dev22 дефект — вкладка «Информация» у машины без мотора пустая (игра читает данные мотора через `CarLoader.GetEngine()`). Пользователь потребовал мотор не ставить; откат без пересборки — убрать имя из cfg `BuildJobStripMethods`.
- **`configVersion` обязан принадлежать нашей машине, а не шаблону** (0.3.11-dev24, CRITICAL — вечный завис на экране загрузки): игра грузит машину заказа **по индексу конфигурации** — `config.txt` = 0, `config1.txt` = 1, `config2.txt` = 2 — и берёт этот индекс из `job.configVersion`. Прежний код копировал поле из ванильного задания-шаблона, то есть индекс чужой машины. Первичный прогон (Player.log): `TakeJob() 32` → `LoadCar() car_porsche964rs 1` → `Cannot load config 1 for car car_porsche964rs! Loading aborted!` → `PrepareJob() Car loader does not loaded car` → `NullReferenceException at CarLoader.SetCarPaintType` в `OrderGenerator+<TakeJob>d__19.MoveNext` (далее NRE в `CarLoader.DeleteCar`) — корутина принятия игры умирает, загрузочный экран не уходит никогда. **Молча чинить это в `TakeJob` нельзя** — игра не оставляет точки, где мод мог бы отменить загрузку. Теперь: `CarData.GetConfigVariantCount(carFile)` считает последовательные `config*.txt` папки машины (кэш; лезет только в папки, уже разобранные в `_carYear`), `TryCreateJob` ставит индекс `Random.Range(0, variants)` и **не создаёт задание** при `variants == 0` (`job skipped: car … has no config the game loader can reach`), а строка предложения печатает `config=N/M`. В пуле 101 ретро-машины 49 имеют только `config.txt` — это 48 % заказов с гарантированным зависанием; две машины, которые в dev22 приехали нормально (`BoltChapman`, `FMWPanther`), как раз имеют `config1.txt`.
- **Индекс живёт в сейве, поэтому чужие заказы нельзя трогать, а свои — надо** (0.3.11-dev24): плохой `configVersion` уже сериализован в предложении, и игрок, принявший такой заказ, зависает снова. postfix `OrderGenerator.GenerateNewJob` вызывает `RepairJobConfigVersions` по `generator.Jobs` **и** `generator.selectedJobs`: правится **только** наше задание (`IsBuildJob`), и только когда индекс не влезает в число конфигов машины (`job config repaired: id=… configVersion 1 -> 0`). Ванильные заказы не меняются (их индексы игровые), исчезнувшая папка машины логируется один раз на id (`job config unknown: …`) и не правится. Это третье разрешённое действие над списком заказов в том же postfix — член списка не добавляется и не удаляется, меняется поле собственного задания.
- Принятие задания захватывается в **prefix** `TakeJob` (id/carFile/carLoaderID): игра может убрать принятый заказ из списка до postfix, и полагаться на поиск в postfix нельзя.
- Активное задание сверяется со списком в postfix `GenerateNewJob` (`ReconcileActiveJob`): если задания больше нет (срок/удаление), состояние сбрасывается, иначе новые сборки не генерируются никогда.
- **Принятое задание приезжает голым остовом — это требование пользователя, а не настройка.** Дефолт `BuildJobStripMethods` = `CreateEngine,CreateEngineAsync,CreateInterior,CreateParts,CreateDriveshaft,CreateExterior,CreateCarLightParts,CreateBonusParts` (0.3.11-dev20; **с 0.3.11-dev22 без `CreateEngine`/`CreateEngineAsync`, с 0.3.11-dev23 без `CreateInterior`** — см. правила ниже): на машине задания не должно быть ни двигателя, ни систем, ни ходовой, ни салона, ни запчастей — только шасси, колёса и снятые панели. Сокращённый набор dev18 (`CreateExterior,CreateCarLightParts,CreateBonusParts`) живым прогоном дал ровно то, что запрещает ТЗ: мотор, детали и салон на остове.
- **Список работы в заказе живёт от деталей машины, и при остове он пуст — это осознанная плата.** Игра наполняет «ДЕТАЛИ ДЛЯ РЕМОНТА» из реально установленных деталей (`OrderGenerator.PrepareJob` → `PreparePart`/`PrepareBodyParts`), поэтому при полном подавлении в списке остаётся замена масла, а вкладки мотора и салона пустые (подтверждено live). Наполнять список модом нельзя: `jobParts` строит игра, а завершение задания считает мод по `Validate` (кузов/детали/рама/интерьер + `BuildJobMinMountedParts` + все детали установлены), поэтому пустой список не делает заказ незавершаемым. Пустой список — не причина возвращать детали на машину.
- **Кузовные панели нельзя снять подавлением** — они приезжают вместе с шасси (`CreateChassis`), а `[9_exterior]` конфига машины содержит только номерные знаки (подтверждено live: `CreateExterior` подавлен, кузов на месте). Единственный легальный путь — игровой `CarLoader.SetRandomMissingPanels(chance)`; вызывается из postfix `CreateChassis` и prefix `PrepareJob` (последний — после полной загрузки машины и до построения списка деталей, поэтому кузовная работа выпадает и из списка). `TryStrip` обязан быть идемпотентным на id задания: оба call-site срабатывают на одной машине.
- **Требование по кузову при снятых панелях = «не измеряется», а не 0 %**: `BodyConditionFor` возвращает −1 когда зачистка панелей активна и ни одна панель не установлена; этот sentinel обязан миновать `Percent` (`Mathf.Clamp01(-1) = 0`), сравнение в `Validate` идёт только при `>= 0`, `IsRequirementMet(0)` возвращает true (тот же контракт, что у рамы). Счётчики «снято»/«установлено» при активной зачистке считают **только не-панели**: снятые панели иначе блокируют завершение через `BuildJobRequireAllPartsMounted` и надувают `BuildJobMinMountedParts`.
- **Принятие не считается состоявшимся по одному исчезновению заказа.** Заказ уходит из `generator.Jobs` и при отказе/отмене, и при истечении предложения, поэтому `BuildJobState.CandidateJobId` пишется в prefix принятия, `ExpireStaleOffer` откладывает срок (`offer expiry deferred`, +60 с) пока кандидат висит, а `CancelJob` снимает кандидата (`cancelled before commit`). Дедлайн кандидата — время (`CandidateTimeoutSeconds = 60`), а не только счётчик вызовов: `UpdateJobs` зовёт `TryCommit` напрямую, и счётчик мог кончиться посреди загрузки машины; при `generator == null` кандидат тоже снимается по дедлайну.
- **Commit требует положительного подтверждения** (0.3.11-dev19, ревью): «заказа нет в `generator.Jobs`» — необходимое, но **недостаточное** условие (так же выглядит отказ, отмену и истечение предложения). `BuildJobAcceptPatch.IsAcceptConfirmed` дополнительно требует id в `generator.selectedJobs` **или** машину с `CarLoader.orderConnection == id`; без подтверждения кандидат продолжает ждать до своего дедлайна. Отключённый мод (F9) обязан **снимать** кандидата, а не подтверждать: `RealParts.OnUpdate` вызывает `BuildJobState.Tick()` + `BuildJobAcceptPatch.AbandonCandidate("mod disabled")` до `return` по `_modIsEnable` (иначе префиксы подавления продолжают работать при выключенном моде, а окно зачистки висит до 60 с и способно зачистить обычную машину той же модели).
- **Колёса и подвеска с остова не снимаются — их делают убитыми по качеству** (0.3.11-dev21, требование пользователя «сделай раму и то, что осталось, 1 % по качеству»): колёса несъёмны (подавление `CreateWheels`/`CreateWheelsIO` вешает приезд, live), а подвеска приезжает вместе с шасси — секция `[2_suspension]` конфига машины, `CreateParts` её не создаёт, поэтому подавление методов над ней бессильно (как и над панелями). Вместо снятия `BuildJobCondition.TryApply` ставит оставшемуся `BuildJobStripConditionPercent` (дефолт **1** %; 0 = выключено): игровой `CarLoader.SetConditionAll(f)` (его путь обновляет визуал ржавчины) + по каждой детали `CarPart.Condition`, `CarPart.ConditionPaint`, `CarPart.StructureCondition`. `StructureCondition` — это метрика рамы в `FrameCondition`, поэтому требование «рама ≥ X %» на остове перестаёт быть декоративным. Идемпотентность по `jobId` (в том числе через cfg-маркер `BuildJobConditionJobId`), максимум `MaxAttemptsPerSource = 3` попытки **на точку вызова** (счётчик сбрасывается при смене `tag` — `PrepareJob` и `tick` имеют независимые бюджеты; общий лимит на обе точки означал, что три неудачи в prefix навсегда отключают фолбэк-тик, находка ревью 0.3.11-dev21), лог `condition strip: job=… percent=…% parts=… attempts=… via=…`, маркер сбрасывается в `BuildJobState.ClearActiveJob`. Запись свойств идемпотентна, поэтому повторный проход сходится; частичное применение (исключение в середине цикла по деталям) остаётся **принятым** риском: задача не помечается применённой и повторяется, а «собрать список заранее» не убирает саму ошибку interop.
- **Состояние обязано применяться во время приезда машины, а не только после commit** (0.3.11-dev22, по live-логу): заказ отменили до commit (`cancelled before commit: id=26`), `PrepareJob` не наступил, `ActiveJobId` не выставлен — и машина приехала с кузовом и шасси в исходном состоянии, то есть требование «1 %» не выполнено ни на одной точке. Третья (главная) точка — prefix `CarLoader.CreateBonusParts`: на нём загрузка конструкторов закончена (панели уже сняты в postfix `CreateChassis`, колёса созданы), опознание идёт через `BuildJobStripTarget.MatchesExact` (см. правило про точную идентичность) **независимо от того, есть ли `CreateBonusParts` в списке подавления** (иначе удаление имени из cfg молча убивает и применение состояния), id берётся как `ActiveJobId >= 0 ? ActiveJobId : ArmJobId`, всё тело prefix обёрнуто в `try/catch` (`CreateBonusParts strip hook failed`, при исключении `return true`). Порядок применения **(0.3.11-dev23, заменено)**: стадии `StageArrival` (prefix `CreateBonusParts`) → `StageEngine` (postfix `CreateEngine`/`CreateEngineAsync`) → `StagePrepare` (postfix `PrepareJob`) → `StageWatchdog` (тик); точка **более поздней стадии применяет повторно**, маркер в cfg пишется только с `StagePrepare` — см. правило про стадии.
- **Необратимая запись состояния требует точной идентичности машины** (0.3.11-dev22, CRITICAL по итогам ревью): `BuildJobStripTarget.Matches` включает фолбэк «место + модель» (он срабатывает при `orderConnection <= 0`, то есть на обычной машине той же модели на вооружённом месте, пока окно открыто). Для подавления деталей это приемлемый риск, для записи 1 % качества — нет (её нельзя отменить, и маркер «применено» затем пропускает настоящую машину задания). Состояние применяется только по `BuildJobStripTarget.MatchesExact`: `orderConnection == ActiveJobId` (если задание активно) либо `MatchesArmedJob(orderConnection)` (окно открыто и id совпадает). Фолбэк «место+модель» не имеет права писать состояние и ставить маркер.
- **Хук состояния обязан оборачивать в `try/catch` ВСЁ тело prefix, а не только свой вызов** (0.3.11-dev22, CRITICAL по итогам ревью): `IsBuildCar`/`IsMethodEnabled` читают `loader.orderConnection`/`placeNo` и парсят cfg-список — исключение interop из-за их предела наружу рвётся в `CarLoader.CreateBonusParts`. При исключении prefix возвращает `true` (игру не ломаем, подавление на этом методе просто не применяется), лог `CreateBonusParts strip hook failed`.
- **Тик фолбэка обязан покрывать и вооружённый id** (0.3.11-dev22, HIGH): при отмене до commit `ActiveJobId == -1`, и если проход в `CreateBonusParts` застал пустой `carParts`, фолбэк на `ActiveJobId` никогда не повторил бы попытку — ровно тот сценарий, ради которого точка добавлена. Тик берёт `ActiveJobId >= 0 ? ActiveJobId : ArmJobId` (после `DisarmStrip` он −1, то есть на отменённом задании тик молчит).
- **Провал `SetConditionAll` не даёт права ставить маркер «применено»** (0.3.11-dev22, HIGH): если игровой путь обновить состояние (визуал ржавчины) бросил исключение, цикл по деталям всё равно записал значения, но подтверждение не получено → `return false` с логом `condition strip not confirmed`, маркеры (память и cfg) не пишутся, остальные точки продолжают пытаться. Игровой `SetConditionAll` **сам запатчен** модом: prefix `JunkyardDonorConditionAllPatch` масштабирует аргумент `condition` (`JunkyardDonorConditionCore.Apply`) для моделей из свалочного набора — итоговое значение всё равно ставит наш цикл по деталям, поэтому это **принятый** эффект (в логе может мелькнуть donor-строка).
- **Грязь — отдельный ключ, по умолчанию 100 %** (0.3.11-dev22): `BuildJobStripDustPercent` (0 = выключено) пишется в `CarPart.Dust` тем же проходом; `CarLoader.SetConditionAll` грязь не трогает, `TweenInteriorConditionAndDust` — корутина с анимацией, прямой запись проще и предсказуемее. Лог: `condition strip: job=… percent=1% dust=100% parts=… via=…`.
- **Состояние применяется стадийно, потому что игра пишет состояние ПОСЛЕ нас** (0.3.11-dev23, корень дефекта по live-логу): зачистка отработала в prefix `CreateBonusParts` (`condition strip: job=30 percent=1% parts=24`), а в игре итог был **ДЕТАЛИ 66 %, ИНТЕРЬЕР 67 %, РАМА 69 %** — ровно значения требований заказа (`body>=81% parts>=67% frame>=65% interior>=75%`). Причина: двигатель игра создаёт **после** `CreateBonusParts`, свои проходы состояния делает ещё позже, а маркер «применено» от первой точки заставлял все поздние точки выходить молча. Теперь у точки есть стадия (`StageArrival=1`, `StageEngine=2`, `StagePrepare=3`, `StageWatchdog=4`), и `TryApply` применяет заново при `stage >= _appliedStage`; маркер в cfg пишется только с `StagePrepare`, тик ограничен бюджетом `BuildJobConditionReapplyMax` (8). `IsApplied` как публичный гейт удалён (единственный читатель маркера — приватный `IsPersisted`), лог `condition strip skipped: … marker from cfg` вместе с ним исчез.
- **Любая запись состояния живёт только внутри guard-окна** (0.3.11-dev23): окно открывает `BuildJobStripArm.ArmCandidate` (prefix принятия), закрывают `BuildJobState.ClearActiveJob` (отмена и выплата в `EndJob`), `BuildJobAcceptPatch.ClearCandidate` и истечение окна зачистки; жёсткий потолок — `GuardMaxSeconds = 60` от открытия, продление — по `BuildJobConditionGuardSeconds` (15) от последней записи. Вне окна не пишет **ни одна** точка (ни prefix, ни postfix, ни тик), поэтому перезапуск процесса с активным заданием не может затереть уже отремонтированную машину: окно живёт в памяти, а cfg-маркер дополнительно запрещает запись после persist. Идентичность — `CarLoader.orderConnection == _guardJobId` (фолбэк «место+модель» писать состояние по-прежнему не имеет права). Логи: `condition guard open: job=… seconds=…`, `condition guard closed: job=… (<причина>)`, `condition guard: game writes forced to 1% (first via …)`.
- **Перехват игровых писателей состояния — отдельный файл `Patches/JobConditionPatches.cs`** (0.3.11-dev23): префиксы `CarLoader.SetCondition`, `SetConditionOnBody` (обе перегрузки), `SetConditionOnDetails(float, Il2CppStringArray)`, `SetRandomPartsConditions(min,max)`, `SetMountObjectsRandomCondition`, `TweenInteriorConditionAndDust(targetCondition,targetDust,time)` (пыль → `BuildJobStripDustPercent`) форсируют `ref`-аргументы через `BuildJobCondition.ForceCondition/ForceDust/ForceRange`; postfix `CreateEngine`/`CreateEngineAsync` (стадия 2) и postfix `PrepareJob` (стадия 3) зовут `TryApply`. `SetConditionAll` и `SetConditionOnDetails(float)` **не** вынесены в отдельный префикс: их форсит явный вызов в конце `JunkyardDonorCondition*`-префиксов (см. правило про приоритет Harmony в `Patches/AGENTS.md`). Ре-ентраность безопасна: `TryApply` зовёт `SetConditionAll`, его префикс только переписывает аргумент тем же значением и обратно не входит.
- **Интерьер приезжает и получает 1 %; пустой салон показать 1 % нельзя** (0.3.11-dev23, требование пользователя «интерьер 67 % — исправить на 1 %»): `CreateInterior` убран из дефолтного `BuildJobStripMethods` (миграция `MigrateStripMethods` подменяет значение **только** при точном совпадении со старым дефолтом, пользовательский список не трогается, лог `cfg strip methods migrated`). Обоснование: у `CarLoader` нет списка деталей салона (в дампе есть только `CreateInterior`, `SetInterior`, `GetInteriorCondition`, `InteriorParams`), а `CarPart` не несёт категории — при пустом салоне писать 1 % некуда, и игра сама рисует свой дефолт (67 % в live-прогоне). Цена решения: салон на машине задания присутствует, и требование по интерьеру игра проверяет по `GetInteriorCondition`, то есть его придётся восстанавливать.
- **Тексты задания не зависят от cfg и от кодовой страницы компилятора** (0.3.11-dev23): русские дефолты живут в `Jobs/BuildJobTextRu.cs` (файл **UTF-8 с BOM**), `BuildJobText.Pick` берёт значение из cfg только если `BuildJobTextRu.IsUsable` его пропускает (пусто / `U+FFFD` / ни одной буквы / ≥2 символа в `U+00C0..U+00FF` = mojibake → дефолт из кода), а `Config.RepairBuildJobConfig()` (вызывается из `RealParts.OnApplicationStart` после `Reload`) чинит 10 текстовых записей и один раз пишет `MelonPreferences.Save()`, логи `cfg repaired: textKeys=… stripMethods=…` и Warning на каждый ключ. Литералы `Config.cs` переведены в \uXXXX (ASCII-исходник), комментарии остались CP1251.
- **Точка применения состояния обязана иметь фолбэк** (0.3.11-dev21): основной вызов — prefix `OrderGenerator.PrepareJob` (машина полностью собрана, список задач ещё не построен), фолбэк — тик `BuildJobService.TickOffers` (каждые 30 кадров, пока активное задание не помеченным применённым: `FindCarLoaderByOrder(ActiveJobId)`). Причина фолбэка: в live-логе dev20 `PrepareJob` не наступил ни разу при отмене заказа до commit, то есть одна точка не покрывает все сценарии.
- **Применение состояния обязано ждать готовности машины и не имеет права помечать «применено» на пустом списке** (0.3.11-dev21, CRITICAL по итогам ревью): тик стартует в момент commit, а машина задания в этот момент может грузиться, и `carParts` ещё пуст. Ранний код засчитывал успех при `parts = 0`, ставил маркер и закрывал путь основному вызову `PrepareJob` (он выходит по `IsApplied`), то есть машина оставалась частично зачищенной с логом об успехе. Теперь: `carParts == null`/пустой/ошибка чтения → `LogWaiting` (один раз на задание) и `return false` **без расхода попытки**; успех засчитывается только при `parts > 0`. Лимит `MaxAttemptsPerSource = 3` тратится только на реальные попытки, поэтому тик не сжигает бюджет за ~1.5 с до окончания загрузки; при исчерпании — один Warning `condition strip abandoned`.
- **Маркер «зачищено» обязан переживать перезапуск процесса** (0.3.11-dev21, HIGH по итогам ревью): `ActiveJobId` и память мода при рестарте обнуляются, а состояние машины живёт в сейве. Без персистентного маркера `PrepareJob` при загрузке сейва с активным заданием применяется повторно и **стирает уже отремонтированные детали**. Маркер хранится в cfg (`BuildJobConditionJobId`, дефолт −1, `RememberConditionJob`/`ClearConditionJob` по образцу предоплаты), проверяется в `IsApplied` и снимается в `ClearActiveJob`.
- **Применение состояния обязано слушаться выключения мода (F9)** (0.3.11-dev21): запись необратима (стирает ремонт), а префиксы Harmony продолжают работать при `_modIsEnable == false` — `RealParts.OnUpdate` останавливает только тики. `BuildJobCondition.Percent()` возвращает 0 при `RealParts.ModIsEnabled == false` (статический флаг, обновляемый в обработчике хоткея вместе с `_modIsEnable`).
- **`CarLoader.SetRandomMissingSuspension(chanceToComplete, chanceToMissing, minMissingParts, maxMissingParts)` существует в игре** (дампу `Assembly-CSharp-firstpass.dll`), но в код не введён: семантика четырёх параметров не подтверждена ни дампом тел (IL2CPP-заглушки), ни live. Снятие подвески — отдельная задача с live-проверкой; молча вызывать с угаданными аргументами запрещено.
- **Задачи кузова не создаются, когда панели снимаются** (0.3.11-dev19): `BuildTasks` пропускает записи `Body|*` из `TaskSpecs` при `PanelsSuppressed()`, иначе заказ на машине без панелей содержит задачу «кузов/покраска», которую игра не может закрыть, а `Validate` не проверяет `jobTasks` → завершение недостижимо. Лог: `tasks built: N of M bodyTasks=omitted (panels stripped)`.
- **Отмена возвращает предоплату и когда задание не активно** (0.3.11-dev19): `ActiveJobId` живёт только в памяти, а предоплата — в cfg, поэтому после перезагрузки сейва отмена заказа обязана звать `ForfeitAdvance` по признаку `AdvanceFor(jobId) > 0` (лог `cancelled: id=… not active, advance clawed back`), иначе 30 % остаются игроку навсегда.
- **Гейт кузова привязан к фактическому снятию панелей на этой машине, а не к шансу** (0.3.11-dev19, по итогам ревью): `BuildJobPanels.PanelsStrippedOn(loader)` = `PanelsSuppressed()` (шанс **или** `CreateExterior` в списке) **и** ноль установленных панелей при успешно прочитанном списке. Именно его используют `BodyConditionFor` (sentinel −1), `CountMounted` и `CountUnmounted` (счёт без панелей). Раньше все три опирались на `PanelsSuppressed()` — конфигурационный признак: при `BuildJobStripPanelChance > 0`, но реально неснятых панелях счётчики молча вычитали панели и занижали `BuildJobMinMountedParts`. Счётчик панелей различает «ноль» и «не удалось прочитать» (`CountMountedPanelsKnown`): при ошибке interop sentinel **не** применяется, требование проверяется по игровому `GetBodyCondition()` (fail closed). `CountMounted` без зачистки считает только установленные детали (раньше возвращал `parts.Count`, включая снятые, и обходил `BuildJobMinMountedParts`).
- **`PanelsSuppressed()` проверяет подавление `CreateExterior` точным именем** (0.3.11-dev20): `BuildJobStripTarget.IsMethodEnabled("CreateExterior")`, а не подстрокой в `BuildJobStripMethods`. Подстрока делала гейт кузова зависимым от ручных правок cfg: отсутствие `CreateExterior` при наличии более длинного имени с тем же префиксом молча переключало требование кузова с «не измеряется» на «измеряется по 0 %». Тот же источник истины, что у префиксов подавления, — один и тот же разбор списка (кеширование по сырому значению, фолбэк на дефолт, Warning на незнакомые имена).
- **`TryStrip` помечает задание снятым только при `effective=true` И `mounted == 0`** (0.3.11-dev19): при `BuildJobStripPanelChance < 100` один вызов снимает часть панелей, и пометка «готово» по первому частичному успеху закрыла бы повторы — машина осталась бы с кузовом. Повторы ограничены `MaxAttemptsPerJob = 3` и: вызов на `CreateChassis` может прийти до появления панелей, и пометка «готово» на пустом вызове навсегда отключила бы поздний вызов `PrepareJob`. Строка лога печатает `before=… effective=… attempts=… via=…`.
- **Commit принятия обязан крутиться вне UI.** Игра не обновляет окно заказов после принятия, поэтому commit только в postfix `AcceptOrderAction` и в `UpdateJobs` в live не наступал ни разу (нет `accepted`, нет предоплаты, нет активного задания и гейта, окно зачистки живёт все 20000 кадров). `BuildJobAcceptPatch.TickCommit()` вызывается из `RealParts.OnUpdate` каждые 30 кадров пока есть кандидат; это же ограничивает отказ принятия ~60 с (`CandidateMaxWaits`).
- Требования не хранить: они выводятся из `job.id` хешем (тот же приём, что `MaxQualityService.HashUid` для rarity). Новая ось требования = новый `stream`-индекс в `Roll`, иначе сдвинутся значения уже выданных заданий.
- `jobType` заполняется флагами `true` на всю длину шаблона **осознанно** (полная сборка = все категории); длина берётся из ванильного задания, массив копируется, а не делится ссылкой.
- Награда начисляется **после** выплаты игры (`GlobalData.AddPlayerMoney` в postfix `GameScript.EndJob`) и защищена от повтора множеством `PaidJobs`; поля `TotalPayout`/`JobBonus`/`TaskBonus` не трогать — формула выплаты игровая.
- «Остов» делается подавлением `CarLoader.Create*` (см. `Patches/CarStripPatches.cs`), а не синтетическим `carFile`: файлы машин — UnityFS-бандлы, вручную они не собираются. Дефолт `BuildJobStripMode = suppress`; `off` — аварийный выключатель (при нём `Matches` выходит сразу и `ArmStrip` не вызывается, то есть приехавшая «заполненная» машина = выключенный режим, а не сломанный хук).
- Арминг окна зачистки обязан открываться **до тела игры**: `BuildJobStripArm.ArmCandidate` вызывается в prefix `OrdersWindow.AcceptOrderAction`. Причина: машина задания грузится внутри принятия, и арминг только в commit (postfix/`UpdateJobs`) может не успеть ни до одного `Create*` — игрок увидит собранную машину. Commit (`OnOrderAccepted`) обязан **закрыть** окно (`strip disarmed: accepted`) и выставить `ActiveJobId`: остаток загрузки подавляется точным путём `orderConnection == ActiveJobId`, переарм окна запрещён (см. правило ниже).
- Окно зачистки привязано к заданию, а не только к модели: `BuildJobState.ArmStrip(jobId, carFile, place)` хранит `ArmJobId`/`ArmPlace`, `MatchesArmedJob(orderConnection)` даёт точное совпадение по id заказа. Любая ветка «окно открыто, но принятие не подтверждено» обязана его закрывать: `BuildJobAcceptPatch.ClearCandidate` вызывает `DisarmStrip`, а лимит `CandidateMaxWaits = 120` подтверждений гасит зависший кандидат (иначе открытое окно + совпадение модели зачистит обычную машину той же модели).
- Опознание машины остова двухуровневое: точно `CarLoader.orderConnection == ActiveJobId` (без окна) или `== ArmJobId` при открытом окне; иначе — открытое окно зачистки **и** `placeNo == ActivePlace` (при активном задании) / `ArmPlace` (по кандидату) **и** точное (не префиксное) совпадение модели. Без проверки места зачистка заденет обычную машину той же модели игрока.
- **Колёса подавлять нельзя.** Подтверждено live: подавление `CreateWheels` обрывает корутину приезда — игра остаётся на загрузочном экране навсегда (в логе последняя строка `strip: skipped CreateWheels`). Поэтому набор подавляемых методов — конфиг `BuildJobStripMethods` (список имён через запятую), и `CreateWheels`/`CreateWheelsIO` в дефолт не входят. Если зависание повторится на другом методе — этот метод убирается из cfg без пересборки; виновника показывает последняя строка `strip: skipped <метод>` перед зависанием.
- Порядок создания машины задания в live: `CreateChassis` (20:49:30) → `CreateWheels` (20:49:33) → остальное. Окно зачистки обязано быть открыто до `CreateChassis`.
- Единицы места **подтверждены live обратным**: во время приезда `CarLoader.placeNo == -1`, поэтому фолбэк «место+модель» на приезде не срабатывает никогда — работает только точный `orderConnection`. И он же надёжен: в момент первого `Create*` поле `orderConnection` уже равно id заказа (лог `strip: skipped CreateWheels … order=13`).
- `activeJob=-1` в момент первой подавления подтверждает: арминг обязан быть в prefix принятия, commit (`OnOrderAccepted`) к этому моменту ещё не выполнен.
- `CarLoader.CreateEngineAsync` подавляется наравне с `CreateEngine` (игра может грузить двигатель корутиной); `CreateChassis` и `CreateChassisAsync` не подавляются — на остове обязано оставаться шасси.
- Счётчик ожидания кандидата обнуляется **в prefix** при каждом новом кандидате: перенесённый от отказанного принятия счётчик заставил бы лимит 120 сработать на первом же обновлении и закрыть окно посреди легитимной загрузки.
- Prefix, не нашедший нашего заказа (принят ванильный заказ), обязан закрыть окно **кандидата** (`BuildJobStripArm.DisarmCandidateWindow`); окно активного задания не трогается — оно нужно для поздней загрузки и защищено точным `orderConnection`.
- Фолбэк «место+модель» живёт только первые `ModelFallbackFrames` (1800 кадров ≈ 30 с) окна, точный путь по id заказа — всё окно (20000 кадров). Причина: у обычной машины `orderConnection == 0`, и без временного ограничения совпадение места и модели зачищает её через минуты после принятия.
- Подавление помечает задание: `BuildJobStripTarget.IsBuildCar` вызывает `BuildJobState.MarkStripped`; `OnOrderAccepted` **никогда не переармивает** окно — он только пишет `strip applied: id=…` либо `strip not applied before commit: id=… - the active job id covers the rest of the load` (это **не** Warning: commit часто наступает до начала загрузки, и подавление тогда впереди) и закрывает окно (`strip disarmed: accepted`). Маркер нужен для диагностики (`stripped=yes|no` в логе истечения) и сбрасывается в `ClearActiveJob`. Причина запрета на переарм: открытое после загрузки окно с фолбэком «место+модель» способно зачистить обычную машину той же модели, поставленную на это место.
- Единицы места в фолбэке **не подтверждены**: `job.carLoaderID` — индекс из `CarLoaderPlaces.GetCarLoaderIndex`, а сравнивается он с `CarLoader.placeNo`. Проверка только live: пара строк `[BuildJob] strip armed: job=… place=…` и `[BuildJob] strip: skipped … place=…`. При расхождении работает только точный путь по `orderConnection`, фолбэк молчит.
- Истечение окна логируется как `strip window expired: job=<id> stripped=yes|no` — поле `stripped` обязательно: без него истечение после успешной зачистки читается как «ничего не подавлялось».
- **Принятый заказ исчезает из `generator.Jobs` — это норма.** `ReconcileActiveJob` (postfix `GenerateNewJob`) обязан считать активное задание пропавшим только если его нет **и** в `generator.Jobs` (предложения), **и** в `generator.selectedJobs` (принятые). Прежний предикат «нет в `generator.Jobs`» совпадал с предикатом commit, поэтому первая же генерация нового заказа после принятия стирала активное задание: снималась предоплата (`ForfeitAdvance`), отключались гейт завершения и выплата, и обрывалась зачистка — машина дособиралась по ходу загрузки. Проверка `selectedJobs` может только уменьшить ложные снятия. **Null-список — не «отсутствует», а «неизвестно»**: если `generator.Jobs` или `generator.selectedJobs` равны null, снимать нельзя (иначе транзиентный null воспроизводит тот же дефект с потерей предоплаты). Факт нахождения принятого задания в `selectedJobs` логируется один раз (`active job N is in selectedJobs`) — семантика списка не подтверждена live, и при застарелой записи активное задание может не сняться и заблокировать новые предложения.
- **Окно зачистки закрывается в commit (`strip disarmed: accepted`), а не в `CreateBonusParts`.** Подтверждено live: машина приехала с кузовными деталями, потому что окно гасилось на `CreateBonusParts`, а `CreateExterior`/`CreateInterior`/`CreateParts` игра вызывает **после** него и до commit. После commit окно не нужно: `ActiveJobId` уже выставлен и точный путь `orderConnection == ActiveJobId` работает без окна, поэтому остаток загрузки подавляется им. `CreateBonusParts` теперь только подавляет.
- Окно обязано жить от prefix принятия до commit: это единственное окно, покрывающее загрузку машины, которая идёт **до** подтверждения принятия (в логе зависшего прогона `strip armed` 20:49:29, `chassis kept` 20:49:30, `first suppression` 20:49:33 и ни одной строки `accepted:` — commit наступил позже загрузки).
- Окно зачистки обязательно закрывать (`DisarmStrip`) в commit (`accepted`), при отказе принятия (`ClearCandidate`, лимит `CandidateMaxWaits`), в `CancelJob` и `EndJob`: подавление привязано к модели машины, и открытое окно заденет обычную машину той же модели.
- Машина задания ищется по `CarLoader.orderConnection == job.id` (это поле — связь машины с заказом); `carToLoad` — модель машины.
- Место в гараже берётся из `CarLoaderPlaces.GetPlaceForLoadCar()`; если свободного места нет, задание **не создаётся** (Warning в логе) — `carLoaderID = 0` означал бы перезапись занятой машины.
- Ретро-пул существует только при положительном `RemoveCarsOlderThanYear`; при 0/отсутствующем породе задание не создаётся (иначе «только ретро» молча снимается).
- `carFile` строится как `car_` + имя папки машины в нижнем регистре (`car_arezzocortona`) — так же, как имя бандла `car_arezzocortona.cms`; регистр важен.
- Рамка (автомобиль) выбирается **случайно** (`UnityEngine.Random.Range`) и не должна повторять предыдущую (`SetLastCarFile` / `IsLastCarFile`): подряд одна и та же модель выглядит как баг.
- Генерация задания вынесена в `BuildJobService.TryOfferJob`, её вызывают из postfix `GenerateNewJob` и из истечения предложения. Инстанс `OrderGenerator` сохраняется в `BuildJobState.Generator` (статического `Instance` у `OrderGenerator` нет) — без него нечем ни снять предложение, ни найти задание по id.
- Непринятое предложение живёт `BuildJobOfferSeconds` (120 с, реальные секунды `Time.realtimeSinceStartup`), затем удаляется из `generator.Jobs` и сразу создаётся новое. Принятое задание от таймера предложения исключено (`HasActiveJob`). Замена по истечении вызывается с `force = true`: бросок `BuildJobChance` в этом пути запрещён, иначе «меняется каждые две минуты» превращается в «иногда» (шанс 35 % молча пропускает замену).
- Уровень: `BuildJobMinLevel = 1` (задание доступно с первого уровня), `BuildJobMaxLevel = 80` — только окно генерации; уже выданное задание при смене окна не удаляется.
- Генерация предложения **не привязана к таймеру игры**: `TryScheduledOffer` в `TickOffers` создаёт заказ по своему интервалу `BuildJobOfferSeconds` (первая попытка сразу после появления генератора, дальше — раз в интервал) и с `force = true`. Причина найдена в live-прогоне: игра зовёт `OrderGenerator.GenerateNewJob` редко (один вызов на заход), и с шансом `BuildJobChance` 35 % заказ мог не появиться ни разу за сессию.
- Инстанс `OrderGenerator` при отсутствии берётся из сцены: `UnityEngine.Object.FindObjectOfType(OrderGenerator.Il2CppType)` — свойство помечено obsolete (CS0618), поэтому обёрнуто в `#pragma warning disable CS0618`; в UnhollowerBaseLib 0.4.18 **нет** ни `Il2CppSupport.Il2CppType.Of<T>()`, ни голого `Il2CppType.Of<T>()` (CS0103). Скан сцены допустим не чаще одного раза за интервал.
- Пока генератор не найден, повторять попытку через **5 с** (`GeneratorRetrySeconds`), а не через полный `BuildJobOfferSeconds`: в главном меню `OrderGenerator` в сцене нет, и планирование на полный интервал откладывает первый заказ на минуты после входа в гараж. При первой передаче инстанса из хука `GenerateNewJob` вызывается `ResetOfferSchedule()` (первый заказ через `FirstOfferSeconds` = 5 с).
- Все отказывающие ветки `TryOfferJob` (уровень, шанс) обязаны печатать причину (`[BuildJob] offer skipped: …`): молчаливый `return false` делает «заказа нет» неотличимым от поломки.
- Принятие заказа из окна — это `OrdersWindow.AcceptOrderAction` (prefix), а **не** `OrderGenerator.TakeJob`: в live-прогоне хук `TakeJob` не сработал ни разу, и из-за этого не было ни предоплаты, ни включения зачистки. `TakeJob` оставлен запасным путём; обе ветки ведут в `BuildJobService.OnOrderAccepted(job, tag)` с защитой от двойной обработки (`ActiveJobId == job.id`). Принятый заказ определяется **только** по выбранной карточке: `OnOrderItemSelect(OrderItem)` и `OnItemSelect(int)` пишут `SelectedJobId`; скан `orderItems` в поисках «нашего» заказа запрещён — он приводит к фантомному принятию, когда игрок берёт ванильный заказ. Prefix ничего не принимает: он лишь запоминает кандидата, а подтверждение проверяет postfix `AcceptOrderAction` и каждый postfix `UpdateJobs` (`TryCommit`), где признак успеха — заказ исчез из `generator.Jobs`; игра может отказать в принятии (нет свободного места), и тогда состояние активного задания ставить нельзя. Кандидат сбрасывается при отмене (`ClearCandidate`).
- `Percent(float)` внутри `Mathf.Clamp01` → **обрезает снизу до 0**. Любой страж «значение неизвестно» (-1) обязан миновать `Percent`: иначе `-1` превращается в `0%`, строка требования показывает `(0/50%)` и никогда не выполняется, а `IsRequirementMet` не видит признак неизвестности. Проверку `frame < 0` делают до вызова `Percent`.
- `SwapSlots` (обмен `GetSiblingIndex`/`SetSiblingIndex`) **сам себе обратна**: второй вызов с теми же аргументами возвращает карточку обратно, поэтому перестановка обязана быть идемпотентной — сначала сравнить `GetSiblingIndex` своей карточки с целевым, и менять только при различии. Индексы массива `orderItems` при этом не меняются, так что по ним нельзя судить, карточка уже переставлена или нет.
- В дампе сигнатур `job` у `GameScript` **нет**: `NativeFieldInfoPtr_job` принадлежит вложенному классу корутины `_EndJobCoroutine_d__139`, а `GlobalData.Jobs` — это `int`-счётчик, не список заданий. Активного задания наружу в явном виде нет; признак принятого заказа — отсутствие задания в `generator.Jobs`. Поля и свойства из дампов сигнатур обязаны проверяться на принадлежность классу, а не искаться по имени.
- Строки `Validate` (причины отказа), попапы и строки требований идут через `BuildJobText.Pick`; лишние ячейки списка задач (`issueObjects[i]`, `i >= lines.Length`) гасятся `SetActive(false)`, иначе под нашими строками остаются ванильные задачи задания.
- `Job.timeToEnd` — **часы**, не дни: значение 7 игра показывала как «00:07». Дни задаются множителем 24 (`BuildJobDeadlineDays * 24`).
- Рама: у `CarLoader` нет геттера рамы; группа «РАМА» в игре = среднее `CarPart.StructureCondition` по установленным деталям (`part.Unmounted` пропускаются). Пустой список деталей → `-1`: требование по раме не проверяется, молчание лучше ложного нуля.
- Разблокировка ячеек заказов: `OrderItem.SetLocked(false)` в postfix `OrdersWindow.UpdateJobs` по флагу `BuildJobUnlockAllOrderSlots` — именно postfix, игра проставляет локи сама в том же `UpdateJobs`.
- Тексты, которые видит игрок, обязаны идти через `BuildJobText.Pick(key, russianValue)`: RU — значения из cfg, EN — дефолты в коде. Язык: `BuildJobTextLanguage` = `auto`/`ru`/`en`; `auto` → `PlayerPrefs["Language"]` (ключ — предположение, подтверждается стартовым логом `[BuildJob] text language: …`), фолбэк `Application.systemLanguage`. Логи остаются ASCII.
- Заказ вставляется в **начало** `generator.Jobs` (`Insert(0, job)`), а не в конец: окно показывает столько карточек, сколько **разблокированных** слотов, и берёт заказы с начала списка. На 1 уровне разблокировано 2 слота, и заказ, добавленный в конец (`list=3`), не отрисовывался вообще: лог давал `job offered`, в окне карточки не было. Плата за это — один ванильный заказ уезжает за видимый диапазон (остаётся в списке и живёт своим таймером).
- Повторяющиеся предупреждения дедуплицируются (первый раз + каждые 12 попыток, счётчик сбрасывается при успехе): `scheduled offer skipped` в главном меню сыпался каждые 5 с и забивал лог.
- Предоплата `BuildJobAdvancePercent` (30 %) считается от награды (цена **готовой** машины × множитель, `TryFinishedPrice` с cond = 1) и выплачивается, когда машина задания появилась и цена известна — то есть через секунды после принятия, а не в момент клика. Сумма обязательна к persist (`RememberAdvance` → `BuildJobAdvanceJobId/Amount`): без неё итоговая выплата не знает, что удерживать, и игрок получает 130 %.
- Итоговая выплата = награда − предоплата (`ClearAdvance` после выплаты). Процент **нельзя** прогонять через `ClampReward`: пол награды (`BuildJobRewardFloor` = 20000) поднял бы предоплату до 100 % дешёвого заказа, и итоговая выплата стала бы 0; предоплата зажимается только в `[0, reward]`.
- Отмена (и исчезновение) активного задания **возвращает** предоплату в бюджет (`ForfeitAdvance` → `AddPlayerMoney(-advance)` + `ClearAdvance`): без этого приём и отмена задания крутят бесконечный бесплатный цикл. Баланс может уйти в минус — у `GlobalData` нет `RemovePlayerMoney`, только `AddPlayerMoney`/`SetPlayerMoney`.
- **Выплата предоплаты транзакционна** (0.3.11-dev19): сначала `GlobalData.AddPlayerMoney(advance)` в `try/catch` (исключение → выход **без** снятия маркера, следующий тик повторит), затем `RememberAdvance`, и только потом `ClearAdvancePending`. Порядок «снять маркер → платить» терял предоплату молча при любом исключении в денежном вызове.
- **Дедлайн ожидания машины — реальное время, а не кадры** (0.3.11-dev19): `AdvanceCarTimeoutSeconds = 180` отсчитывается от первого найденного `CarLoader` (`Time.realtimeSinceStartup`); прежние 120 попыток по 30 кадров = 3600 кадров давали ~60 с на 60 FPS и ~25 с на 144 FPS, причём счётчик тратился и до появления машины.
- **Возврат предоплаты снимает метку только при успешном списании** (0.3.11-dev19): `ClearAdvance` внутри `try` после `AddPlayerMoney(-advance)`; при исключении метка остаётся и возврат повторится, иначе «бесплатная» предоплата не возвращается никогда.
- Опрос предоплаты в `TickOffers` троттлится (каждые 30 кадров): поиск машины по `orderConnection` + чтение цены — IL2CPP-interop, в `OnUpdate` каждый кадр это дорого. Ограничение — **реальные секунды** (`AdvanceCarTimeoutSeconds = 180`, отсчёт от момента, когда машина найдена): если цена так и не стала известна, предоплата abandonment с Warning — висящий маркер означает вечный опрос. Кадровый лимит (120 попыток) запрещён: он менялся от FPS.
- Цена **готовой** машины для предоплаты — `TryFinishedPrice` (cond = 1): базовая цена берётся из `CarInfoData.BuyPrice` приехавшей машины, фолбэки — `CarPriceCache`, цена из профиля; на остове живое состояние использовать нельзя (предала бы 30 % от цены хлама).
- `RequirementLines` возвращает 4-ю строку (предоплата), она может быть `null` — вызывающий код обязан пропускать пустые строки **и гасить такой слот** (`IIssueObject.SetActive(false)`), иначе в нём остаётся ванильный текст задачи; `IsRequirementMet` для индекса 3 не вызывать (там предоплата: `done = advance > 0`).
- **Предоплата не считается по списку заказов** (0.3.11-dev19): принятый заказ всегда отсутствует в `generator.Jobs` — это сигнал принятия, поэтому поиск задания в этом списке (`FindJobById`) гарантированно давал «задания нет» и маркер предоплаты снимался молча: 30 % не выплачивались никогда. Предоплата считается по машине задания — `FindCarLoaderByOrder(jobId)` (`CarLoaderPlaces.Get()` + `orderConnection == jobId`), цена — `TryFinishedPrice` (cond = 1).
- **Файлы слоя разбиты под правило «нет файлов > 500 строк»** (0.3.11-dev19): `BuildJobService` — `partial`, продолжения `BuildJobServiceOffers.cs` (тик/предложение/истечение), `BuildJobServiceAdvance.cs` (предоплата, возврат, снятие заказа), `BuildJobServiceValidation.cs` (`Validate`, строки требований, живые значения, счётчики), `BuildJobServicePrices.cs` (цены, награда, задачи, `Roll`/`Hash`). Новый файл слоя обязан быть добавлен в `RealShop.csproj`.

## Чего не делать

- Не добавлять новые поля и схемы сохранения: профиль игры — бинарный `profileN.cms21b`, своя схема = сломанные сейвы.
- Не опрашивать `Get*Condition` в `OnUpdate` — только по событиям UI (`SetupIssues`, `UpdateJobs`, `EndJob`).
- Не менять `OrderGenerator.Jobs` вне двух мест: postfix `GenerateNewJob` (добавление предложения) и `BuildJobService.RemoveJob` из пути истечения предложения (`TickOffers`). Список живёт в `NewJobsData` и сериализуется игрой; мутация в другом месте = рассинхрон с сейвом.
- «Отдельный слот» = последний **разблокированный** `OrderItem` (`isLocked`), а не последний в массиве: на низких уровнях игра блокирует хвост списка (`НЕОБХОДИМЫЙ УРОВЕНЬ n`), и карточка в заблокированном слоте недоступна — со стороны это выглядит как «заказа нет».
- Слой обязан печатать строку установки в `OnInitialize` (`PatchBootstrap.LogBuildJobs`): при выключенном `EnableBuildFromScratchJobs` хуки не срабатывают ни разу, и без стартового лога нельзя отличить «функция выключена» от «патчи не наложились».
- Не полагаться на `Job.timeToEnd` как на подтверждённые «дни»: единицу измерения задаёт игра, значение из `BuildJobDeadlineDays` проверять в live-прогоне.
