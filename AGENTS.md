## Обзор проекта

Каноническое расположение проекта: `D:\dev\src\realshop\` (remote `https://github.com/microup/realshop.git`). Любые копии этого дерева в других папках — снимки для чтения; код менять только здесь.

RealShop — MelonLoader-мод для *Car Mechanic Simulator 2021* (Red Dot Games). C# / .NET Framework **4.8**, `OutputType=Library`, сборка в `RealShop.dll`. Игра собрана на **IL2CPP**, поэтому мод работает через MelonLoader 0.6.1 + UnhollowerBaseLib 0.4.18 и Harmony **2.9.0** (`using Harmony;` + `HarmonyInstance` — это алиасы Harmony 2.x, не устаревшая 1.x). Мод убирает из магазина запчасти машин старше `RemoveCarsOlderThanYear` (2005), вводит restoration ceilings (потолок восстановления, v0.3.9), экономику (sell-cap, labor cost, donor condition), маркеры потребности/апгрейда на свалке (v0.3.10) и условную экономику v0.3.11: цена продажи машины и деталей зависит от состояния, труд — гипербола `1 + k·cond/(1−cond)`, превью цены/прироста следующего цикла на кнопке Start; индикатор маржинальности (`MarginService`, в разработке как 0.3.11-devN): зелёный `$`-маркер на карточках и зелёная/красная раскраска превью, когда цикл ремонта окупается/не окупается (resale-канал детали + канал машины). С 0.3.11-dev5 — кап качества аукциона: звёздный рейтинг каждой аукционной машины зажат к `AuctionMaxRating` (по умолчанию 1); с 0.3.11-dev6 — на аукционе только машины старше `RemoveCarsOlderThanYear` (пул `GetCarsForScene(SceneType.Auction)` + фильтр списка `AuctionManager.GenerateCars`); С 0.3.11-dev21 — **оставшееся на остове убивается по качеству**: колёса снять нельзя (подавление `CreateWheels`/`CreateWheelsIO` вешает приезд), подвеска приезжает с шасси (секция `[2_suspension]`, `CreateParts` её не создаёт), поэтому снятие методов над ней бессильно; вместо этого `RealShop/Jobs/BuildJobCondition.cs` применяет `BuildJobStripConditionPercent` (дефолт 1 %; 0 = выключено): `CarLoader.SetConditionAll` + по каждой детали `Condition`/`ConditionPaint`/`StructureCondition` (рама = среднее `StructureCondition`, то есть требование «рама ≥ X %» становится настоящим гейтом). Вызов — prefix `OrderGenerator.PrepareJob` + фолбэк в тике `TickOffers` (в live `PrepareJob` не наступил при отмене до commit); идемпотентно по id задания, ≤ 3 попыток, лог `condition strip: job=… percent=…% parts=… via=…`. Игровой `CarLoader.SetRandomMissingSuspension(chanceToComplete, chanceToMissing, minMissingParts, maxMissingParts)` в код **не** введён: семантика параметров не подтверждена (тела — IL2CPP-заглушки), вызывать с угаданными аргументами запрещено. **С 0.3.11-dev22** состояние применяется **во время приезда машины** — prefix `CarLoader.CreateBonusParts` стал главной точкой: заказ отменяют до commit (`cancelled before commit`), и тогда ни `PrepareJob`, ни тик не срабатывают — в live машина приехала с целым кузовом и шасси; опознание там идёт **независимо от списка подавления**, id = `ActiveJobId >= 0 ? ActiveJobId : ArmJobId`. Добавлена грязь: `BuildJobStripDustPercent` (дефолт **100** %; 0 = выключено) в `CarPart.Dust` тем же проходом (`SetConditionAll` грязь не трогает). Попытки считаются **на точку вызова** (общий лимит глушил фолбэк), маркер «зачищено» **персистентный** в cfg (`BuildJobConditionJobId`) — иначе `PrepareJob` после рестарта стирает уже отремонтированные детали, и применение слушает выключение мода F9 (`RealParts.ModIsEnabled`), потому что запись необратима. Там же по итогам ревью: опознание для состояния — **только** точное (`MatchesExact`, фолбэк «место+модель» писать 1 % не имеет права), всё тело prefix `CreateBonusParts` в `try/catch`, тик фолбэка берёт и `ArmJobId`, а провал `SetConditionAll` (`condition strip not confirmed`) не даёт ставить маркер. И **мотор больше не подавляется**: дефолт `BuildJobStripMethods` (и живой cfg) без `CreateEngine`/`CreateEngineAsync`, потому что без мотора `CarLoader.GetEngine()` не имеет GameObject, а `EngineTabData`/`MainTabData.SetupData` в окне информации его читают — в live вкладка «Информация» осталась пустой; мотор приезжает и получает 1 % качества наравне с остальным. Кузовные детали убираются игровым механизмом `CarLoader.SetRandomMissingPanels(BuildJobStripPanelChance)` (дефолт 100) из postfix `CarLoader.CreateChassis` и prefix `OrderGenerator.PrepareJob(CarLoader, Job)`: `CreateExterior` панели не создаёт (секция `[9_exterior]` конфига машины — только номерные знаки), панели приезжают вместе с шасси, поэтому их подавление в списке методов бессильно. Требование по кузову пропускается когда панели снимаются и ни одна не установлена (sentinel −1 как у рамы), а счётчики «снято»/«установлено» считают только не-панели, иначе снятые панели делают задание незавершаемым; имена панелей — `BuildJobPanelNamePrefixes` (`CarPart.name` по префиксам). Принятие заказа подтверждается тиком `BuildJobAcceptPatch.TickCommit()` из `RealParts.OnUpdate` (каждые 30 кадров пока есть кандидат): игра не обновляет окно заказов после принятия, поэтому commit только в postfix/`UpdateJobs` в live не наступал никогда — ни предоплаты, ни активного задания, ни гейта завершения, и окно зачистки оставалось открытым все 20000 кадров. С 0.3.11-dev19 — **предоплата перестала теряться**: `TryPayPendingAdvance` искала задание через `FindJobById` только в `generator.Jobs`, а принятый заказ всегда уходит из этого списка (это и есть сигнал принятия), поэтому маркер предоплаты снимался молча и 30 % не выплачивались никогда; теперь предоплата считается по машине (`FindCarLoaderByOrder` по `CarLoader.orderConnection == jobId`), список заказов в расчёте не участвует. **Карточка задания больше не уезжает в самый низ**: `DedicatedSlotIndex` ставит её сразу после карточек доступных заказов (раньше — в последний разблокированный слот, что при `BuildJobUnlockAllOrderSlots` = низ списка), перенос — `SetSiblingIndex` с защитой от повторного перемещения. **Соблюдено правило «нет файлов > 500 строк»**: `Config.cs` (1873) → `Config.cs` + `ConfigInit.cs` + `ConfigCarLists.cs` + `ConfigCarYearsA|B|C.cs` (массив `RetroPartYears` из 1216 записей стал тремя методами, склеенными `RetroPartYearsDefault()`, коды страниц CP1251 сохранены, содержимое сверено построчно); `Jobs/BuildJobService.cs` (1281) → `+Offers/+Advance/+Validation/+Prices` (partial); `Runtime/GarageNeedsRecon.cs` (879) → `+Prices/+Dump`; `Patches/RarityColorPatches.cs` (772) → `+Markers`; `Patches/RepairPatches.cs` (613) → `+RepairLaborPatches/+RepairCostPreviewPatches`; `Patches/EconomyPatches.cs` (527) → `+MoneyAndCarSalePatches`. ## Настройка окружения

- Требуется установленная игра **Car Mechanic Simulator 2021** с **MelonLoader** (проверено на game build 1.0.40).
- **Канонический путь игры: `D:\SteamLibrary\steamapps\common\Car Mechanic Simulator 2021\`**. Все `HintPath` в `.csproj` (21 ссылка) и `OutputPath` — абсолютные, от этого корня. Относительные `..\..\..\..\SteamLibrary\...` в `.csproj` запрещены (не совпадают с реальным расположением диска). Если игра в другом месте — правьте `HintPath` локально и **не коммитьте** это в `.csproj`.
- Конфиг мода создаётся игрой в `D:\SteamLibrary\steamapps\common\Car Mechanic Simulator 2021\Mods\RealShop.cfg` (MelonPreferences); секретов нет.

## Сборка и запуск

```bash
# MSBuild 18 (Visual Studio 18 Community) — проверено, работает:
"C:/Program Files/Microsoft Visual Studio/18/Community/MSBuild/Current/Bin/MSBuild.exe" RealShop.sln //p:Configuration=Debug //v:minimal
```

- NuGet не используется — только прямые `<Reference>` из каталога MelonLoader игры.
- Debug-сборка пишется прямо в `D:\SteamLibrary\steamapps\common\Car Mechanic Simulator 2021\output\` (`OutputPath` в `.csproj`) — оттуда MelonLoader подхватывает `RealShop.dll`.
- **Не использовать** старый `C:/Windows/Microsoft.NET/Framework64/v4.0.30319/MSBuild.exe` — он не понимает C# 6+ (строковые интерполяции `$"..."` в `RealShop.cs`, `Inspect.cs`, `PatchBootstrap.cs`) и даёт ложные `error CS1056`.
- Релиз-архив для Nexus собирается отдельно, только по явному запросу.
- **Тестов в проекте нет и не создавать** без явного запроса. Проверка изменений — сборка + live-запуск игры; мод логирует каждый патч на старте (`[SellCap]`, `[RarityColor]`, `[DonorCond]`, `[Money]`, `[Recon]`, `[BuildJob]`) — по логам видно, какие хуки активны.

## Стиль кода и конвенции

- Один namespace `RealShop`; классы `internal static` для сервисов и патчей.
- Дефолты конфига — `const`/`static` поля в `Config.cs` (`ValuePriceParts*`, `MaxQuality*` и т.д.), наружу — свойства через `MelonPreferences_Entry.Value`.
- Логи только через `MelonLogger.Msg/Warning` с префиксом подсистемы в квадратных скобках.
- Не добавлять комментарии к коду, если об этом явно не просят.
- `#pragma warning disable CS0618` уже расставлен там, где нужны устаревшие MelonLoader API (`OnApplicationStart`, `MelonMod`), — не удалять.

## Архитектура (кратко)

Поток: `RealParts` (MelonMod) → `OnApplicationStart` грузит `Config` и вызывает `PatchBootstrap.Install(harmony)` → `OnSceneWasLoaded(buildIndex==10)` инициализирует `RetroPartCatalog` (цены/скрытие магазина) → `OnUpdate` крутит `SceneUiController` и hotkeys. Игровые типы доступны через `CMS.*` (Assembly-CSharp) и `GameTypes.All()` (кэш рефлексии по сборке игры).

## Запреты и подводные камни

- **Кодировки**: `RealShop/Config.cs` — **Windows-1251** (кириллические комментарии), `RealShop/Inspect.cs` — UTF-8 BOM, остальные — UTF-8 без BOM. При редактировании `Config.cs` сохранять CP1251; не перекодировать файлы «автоматически».
- **`edit_file_tool`/`replace_file` читают файл как UTF-8** — через них `Config.cs` править нельзя (комментарии CP1251 превращаются в мусор): только точечная правка байтов в Python с декодированием и кодированием `cp1251`.
- **Кириллица в исходниках** — только \uXXXX-литералы (как в `Config.cs`) или файл **UTF-8 с BOM** (как `Inspect.cs`, `Jobs/BuildJobTextRu.cs`). Файл UTF-8 **без BOM** с кириллическими строками компилятор может декодировать по ANSI-фолбэку: строки молча портятся, а сборка проходит.
- **`MelonPreferences` и кириллица**: сохранение игры пишет cfg в UTF-8 (`MelonLoader.Preferences.IO.File.Save` → `File.WriteAllText`), `Tomlet` не экранирует не-ASCII, поэтому кириллические значения в cfg живут только при UTF-8-чтении. Любая внешняя правка cfg ASCII-редактором превращает кириллицу в литеральные `?` (число `?` равно числу UTF-8-байт слова), и UI показывает `?????`. Мод обязан чинить такие значения сам (`RepairBuildJobConfig`), а не просить пользователя править cfg.
- **«Колёс нет» измеряется только игровым состоянием** (0.3.11-dev30, live): `missing=None mounted=CanDrive` при 28 отключённых рендерерах — косметика не считается, а объекты `GetWheel*Handle()` не содержат меша шины/диска.
- **Стек вызывающего игрушку-метод не покажет имя** (0.3.11-dev30, live): и `System.Diagnostics.StackTrace`, и `UnityEngine.StackTraceUtility.ExtractStackTrace()` обрываются на `DMD<…>`/`_il2cpp`; дамп firstpass — заглушки `il2cpp_runtime_invoke`. Искать причину надо в данных, которые мод передаёт игре, а не в стеке.
- **`CarLoader.carParts` — это только кузовные панели + агрегаты `body` и `details`** (0.3.11-dev29, live): подвеска и колёса там не живут, поэтому «снять подвеску по префиксу имени» принципиально невозможно; у игры свои методы (`SetRandomMissingSuspension`) и свои состояния (`MissingWheelTypes`, `CheckCarHaveMountedWheel`). Прежде чем писать обход, читать live-список имён (`part names:`).
- **Косметическое скрытие детали ломает её монтаж и пикание** (0.3.11-dev29): выключенный GameObject колеса теряет коллайдеры ⇒ правый клик по машине не открывает радиальное меню, а игра потом не даёт поставить колесо. Убирает деталь игра (подавление конструктора/родной «missing»-метод), мод лишь проверяет состояние.
- **Игровой метод-писатель на подавленной категории бросает NRE** (0.3.11-dev28, live): `TweenInteriorConditionAndDust` на машине без салона падает внутри игры. Состояние «категории нет» делают через форс геттера + компенсацию проверок заказа, а не вызовом игрового писателя.
- **Панель «СОСТОЯНИЕ» показывает состояние игры, а не наши оценки**: форс геттеров `CarLoader` работает только внутри окна guard и ломает `Validate`, если расширить его на всё время задания (0.3.11-dev27, live). Нужные цифры — пишут в игру: `TweenInteriorConditionAndDust` для салона, `CarPart.Unmounted` для деталей, объекты колёс.
- **У колёс нет состояния «отсутствуют» в данных** (0.3.11-dev27): `GetMissingWheelTypes()` только читает, `CarWheelsData`/`Wheel` хранят Tire/Rim/Width/Size/Profile/ET — «нет колеса» = выключенный объект (`GetWheelFL/FR/RL/RRHandle()`).
- **Harmony-префикс в MelonLoader имеет право возвращать только `bool` или `void`** (0.3.11-dev26, live): префикс с другим типом возврата (например `float[]` для `__state`) приводит к `InvalidHarmonyPatchArgumentException` и **весь класс патчей не навешивается**; MelonLoader логирует это одной строкой `[RealShop] [ERROR] HarmonyLib.HarmonyException` в самом начале старта, мод при этом продолжает работать — то есть часть функций молча отсутствует. Состояние передаётся только как `ref <тип> __state`. Префикс, пишущий `__result`, обязан вернуть `false`, иначе оригинал перетирает запись.
- **Игровая машина не умеет ездить без данных мотора** (0.3.11-dev26, live дважды): при подавленном `CreateEngine` вкладка «Информация» пустая (только шильдик), вкладка двигателя без «Вариантов замены». Нужен «мотора нет» — гаси **объект** мотора (`GetEngine().SetActive(false)`), а не его создание.
- **Оценка состояния категории, которой на машине нет, — не 0, а игровая константа** (0.3.11-dev25, live: ИНТЕРЬЕР 66–67 % при подавленном `CreateInterior`): `CarLoader.GetInteriorCondition`/`GetDetailsCondition` на пустом наборе возвращают дефолт игры, поэтому «0 % там, где детали нет» делается форсом геттера, а не записью в детали. Список деталей салона у `CarLoader` отсутствует, так что «пустой салон» опознать по деталям нельзя — источник истины для форса это cfg-список `BuildJobStripMethods`.
- **Список двигателей кузова лежит в конфиге машины, а отображаемые имена — в таблице локализации игры**: `StreamingAssets/Cars/<Car>/config*.txt` секция `[6_engine]` → `swapoptions=engine_…`, а подпись для UI — `StreamingAssets/Localizations/<Language>.txt` строка `!<id>=<имя>` (0.3.11-dev25). Индекс `configVersion` заказа определяет, из какого именно файла читать `swapoptions`.
- **`job.configVersion` — индекс файла конфига машины, а не «версия джобы»** (0.3.11-dev24): игра грузит машину заказа по `config.txt` (0) / `config1.txt` (1) / `config2.txt` (2)…, и индекс берётся из задания. Копировать его из чужого ванильного задания нельзя: при индексе, которого у нашей машины нет, игра пишет `Cannot load config N for car …! Loading aborted!`, роняет свою корутину `TakeJob` NullReferenceException-ом и остаётся на загрузочном экране навсегда (спасения из мода в этой точке нет — только не допускать такого индекса). Чинится счётчиком `config*.txt` на диске: `CarData.GetConfigVariantCount`.
- **Harmony 2.9: приоритет префикса — ловушка.** `PatchInfoSerialization.PriorityComparer` сортирует **по убыванию** приоритета, а значение по умолчанию у префикса без `[HarmonyPriority]` равно **−1**, то есть **ниже** `Priority.Last = 0`. Префикс без приоритета выполняется **последним** и выигрывает запись в `ref`-аргумент у префикса с `Priority.Last`. Если нужно переписать аргумент после чужого префикса, писать нужно **в конец своего префикса на том же методе** (образец: `JunkyardDonorCondition*` + `BuildJobCondition.ForceCondition`), а не заводить отдельный префикс с `Priority.Last`.
- Не править `.csproj` без необходимости; `HintPath`/`OutputPath` — абсолютные от `D:\SteamLibrary\steamapps\common\Car Mechanic Simulator 2021\`, относительные пути запрещены.
- Не трогать `Assets/` (картинки README), `LICENSE*`, `.gitattributes`.
- Хуки на IL2CPP-методы игры ломаются при обновлении игры — любой новый хук обязан логировать успех/провал (образец: `PatchBootstrap.TryPatchSellItem`).
- `ListRetroPartYears` — формат `year|part_id[|rarity]`; третий токен rarity с v0.3.9 **игнорируется** (не удалять из строк конфига молча, совместимость).
- `Config.cs` огромен (~1600 строк, бо́льшая часть — таблицы id деталей); новые id добавлять в существующие массивы, не плодить дубли.
